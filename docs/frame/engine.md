# 引擎模块

[框架目录](README.md)

正式开发采用 Godot 引擎（已定）。四维核心逻辑编写为一个独立的纯 C# 类库，称为**四维引擎**。该类库完全不依赖 Godot，仅通过一组固定的公共接口供 Godot 调用（已定）。

## 分工

- **四维引擎**（纯 C# 项目，不引用 Godot）：维护全部四维空间状态，执行所有四维几何计算，并落实跨截面规则。
- **适配层**（Godot 项目内的 C# 代码）：整个工程中唯一同时认识四维引擎与 Godot 的桥接层。负责从 Godot 场景读取世界描述喂给四维引擎，把玩家与脚本的操作转化为引擎接口调用，再将引擎输出的几何数据与事件转化为 Godot 的网格（Mesh）、碰撞形状（Shape3D）和信号（Signal）。
- **游戏层**（Godot 项目，只用 C#）：负责画面渲染、三维角色控制、音频播放、UI 界面、谜题与剧情脚本，以及编辑器辅助工具。游戏层只通过适配层与四维引擎交互，自身不碰任何四维几何计算。

## 解耦规则

1. **单向依赖**：只有 Godot 项目单向引用四维引擎项目；四维引擎的 `.csproj` 绝不引用任何 Godot 程序集——任何人若在四维引擎里误用了 Godot 类型，编译期就会直接报错拦截。
2. **Godot 侧不做任何四维计算**：物体的四维位置与旋转、截面切片、碰撞检测、支撑高度以及跨截面规则，一律通过接口向四维引擎请求和读取。Godot 侧可以把编排参数传给四维引擎（例如啃食者沿时间轴移动的路径点），但绝不自己在外面算四维几何。
3. **接口契约只使用四维引擎自有类型**：接口签名仅包含基础数值、数组、实体 ID，以及四维引擎自己定义的向量、姿态矩阵与结果结构，不暴露任何 Godot 类型。截面几何统一以顶点坐标、法线、UV 贴图坐标和零件编号的平面数组返回，再由适配层组装成 Godot 的网格与碰撞形状。四维引擎的前三维坐标约定与 Godot 完全一致（单位为米，Y 轴朝上，右手坐标系），适配层转换时只需将内部的 `double` 转为 `float`。
4. **四维引擎不自行计时**：由 Godot 在每帧通过推进接口显式传入时间步长（Delta Time）。只要输入序列相同，输出结果就严格一致，保证自动化测试可完全复现。
5. **四维引擎不触碰外部资源**：不涉及渲染、音频与输入设备，也不直接读写磁盘文件。关卡初始数据由适配层从 Godot 场景树中提取后传入；存档时由四维引擎导出纯状态数据包，交由 Godot 负责落盘保存。
6. **对外只暴露最小固定契约**：仅有接口契约直接用到的类型设为 `public`，引擎内部的数据结构与算法一律设为 `internal`，从语言访问权限上杜绝 Godot 侧绕过接口直接操作内部状态。日后若需调整接口，必须在同一次提交中同步修改适配层。
7. **独立的单元测试工程**：四维引擎配备独立的 `dotnet test` 测试项目，无需启动 Godot 即可直接运行。四维数学按本文档重新设计、重新编写，不翻译原型代码。测试期望值来自可手算的精确几何结果、必须始终成立的几何性质，以及 [尺寸规范](rules.md#尺寸规范) 中由公式算出的数值，不读取原型生成的数据。原型只作为玩法与手感参照。

## 接口

下表确立职责分组；具体类型、方法签名、错误和场景标注见[公共契约](contract.md)（待用户批准）。实现前先确认该契约已获批准。

| 接口分组 | 职责与用途 |
|---|---|
| 世界 | 载入关卡的世界描述：截面列表及其 W 坐标、楼房元素及其 W 范围、缺口区间、固定物件、接缝配置 |
| 实体 | 动态添加与移除可转物件、四维物品、四维装置和各类生物；读取它们当前的四维姿态与状态 |
| 动作 | 规划与执行 F 键、R 键操作（竖起、放倒、翻面）；抓住竖起物体的切面平移、携带四维物品平移；穿过接缝；驱动四维装置旋转或沿截面内 x、y、z 方向的直线轨道平移（位移有上下限，沿用平移碰撞规则，暂不支持沿 W 平移）；修改跨截面共享量。每次请求均返回是否允许执行，受阻时附带阻挡原因与碰撞点信息 |
| 推进 | 由宿主每帧调用一次并传入时间间隔；返回本帧内发生的空间事件（翻转开始与结束、移动受阻、物体下落、穿过接缝、场景结构被啃食等） |
| 截面 | 获取指定截面内所有物体的精确切片几何数据、翻转预览扫过的轨迹轮廓，以及隐藏四维结构的虚线提示轮廓 |
| 查询 | 供谜题与剧情脚本调用的通用状态查询：计算支撑高度、检测某处空间是否被占据、判断某物体在指定截面内是否有切面、计算两点间的四维距离（供跨截面音频衰减与背景音乐分层使用）、比对两件实体的手性是否一致（供进食与开锁判定使用） |
| 存档 | 导出与恢复完整的四维世界状态 |

## 模块

下表列出正式开发的模块职责。序章原型只用于对照玩法与手感，不作为四维算法的实现依据。

**四维引擎内部模块：**

| 模块 | 核心职责 | 处理的内容类别 |
|---|---|---|
| 四维几何 | 四维向量与旋转矩阵、平面旋转变换、各类几何体的精确切片（四维盒子、四维圆环、四维球、线性放样体、隐式元球）、几何碰撞检测（盒子、球体）、支撑高度求解 | 所有需要做四维计算的内容类别 |
| 世界 | 维护截面列表与 W 坐标、楼房元素及其 W 范围与缺口、接缝列表，以及由场景标签生成的静态四维碰撞实体与支撑面 | 楼房、固定物件、接缝 |
| 实体 | 维护可转物件、四维装置、四维物品、四维生物的几何形体与动态状态，以及三维生物所在的截面、四维旋转矩阵和随身携带物品；每类实体统一向上提供切片生成、碰撞体与支撑采样点接口 | 普通物件、四维装置、四维物品、四维生物，以及三维生物的四维状态 |
| 动作 | 判定 F 键与 R 键的具体旋转方案（竖起方向随棱镜当前选中的截面而定：更深则向 +W，更浅则向 −W）、执行翻转途中与携物平移时的碰撞检测、控制翻转角速度节奏、处理穿缝携带规则与长物卡缝、执行原页放倒限制、维护手性变换、驱动四维装置旋转、沿直线轨道平移与共享量更新 | 可转物件、四维物品、四维装置、接缝 |
| 查询 | 向宿主脚本提供无特例的通用物理与空间查询 | 全部类别 |

**Godot 侧模块：**

| 模块 | 核心职责 | 处理的内容类别 |
|---|---|---|
| 适配层 | 从 Godot 场景树提取世界描述；把输入与脚本指令转化为引擎接口调用；把引擎返回的切片数据组装成 Godot 网格与碰撞形状；将引擎事件转发为 Godot 信号 | 全部类别 |
| 截面渲染 | 为每个截面维护独立的 `World3D`（天然保证灯光不跨截面）、使用 `SubViewport` 渲染棱镜镜片内选中的目标截面、实现 PS1 风格渲染管线、绘制翻转预览线、为镜片内的贯穿物叠加发光轮廓、绘制镜像缝周围的像素翻转窄带、观察者处于镜像状态时把整个屏幕（包括镜片）左右翻转 | 全部类别 |
| 三维角色 | 处理角色在当前截面内的移动与常规碰撞（使用 Godot 内置三维物理；四维物体落在该截面内的切片由适配层实时生成碰撞形状）、寻路导航、动画状态机、饥饿度与背包管理；镜像状态下把转向和左右平移的输入方向反过来，与画面翻转相互抵消；穿缝时向四维引擎发起请求 | 三维生物 |
| 四维生物编排 | 管理啃食者的四维移动路径、旋转与张嘴动画的时间轴，每帧将插值后的参数传给四维引擎 | 四维生物 |
| 声音 | 三维空间定位播放；根据四维引擎返回的四维距离实现跨截面低通变闷与背景音乐分层过渡；在镜像缝附近混入倒放环境音 | 表现层 |
| 谜题与剧情脚本 | 管理场景阶段推进、角色台词、操作提示与受阻反馈语音；所有解谜触发条件一律通过通用查询接口读取物理状态 | 不直接碰四维几何 |
| 工具 | Godot 编辑器插件：支持沿 W 轴连续拖动的截面查看器、多截面并排对比视图、翻转轨迹扫过范围可视化、关卡内容合规性自动校验，以及建筑被啃食后各截面残缺网格的离线预计算（底层计算全部调用四维引擎）。游戏内的侧视图（只读观察）与编辑器截面查看器本质上是同一种含 W 平面切片，可复用同一套逻辑 | 全部类别 |

**编辑器内容校验工具需自动检查的数值规范：**

- 可转物件竖起后，是否有零件端面距离任意截面不足 2 厘米；
- 物品的隐藏四维结构在静止时，是否距离任意截面过近；
- 楼房标注的 W 范围，是否完整包住了该楼房内所有可转物品向正反方向竖起后能伸及的范围；
- 同一截面内的两道接缝间距是否小于 0.8 米；
- 关卡内每个谜题的预期解法操作，是否都能顺利通过转动碰撞检查。

**关卡设计与校验流程以人为主**（已定）：谜题构思可以与 AI 协作脑暴；编辑器工具负责把四维空间直观地摆出来给人看（沿 W 轴拖动切片、多截面并排对照、翻转扫过体积高亮），并自动拦截上述硬性数值错误；而“玩家能否仅凭截面变化看懂空间运动”“谜题解法是否直观公平”，最终一律由设计师人工审定。

## 待定问题

暂无。后续开发中出现的新问题统一记录在此处。

**已定技术选型记录**：四维引擎最终选定使用 C# 编写，而非 GDScript 或 C++。原因在于四维几何计算中有几项高频任务需要每帧运行：啃食者的隐式曲面切片（主画面与棱镜镜片每帧各切一次）、旋转途中物体的实时切片、携带四维物体平移时的碰撞检测；此外，举起棱镜预览时每隔 0.15 秒还要重算一次整段旋转碰撞轨迹（原型在浏览器中单次约耗时 7 毫秒）。C# 执行纯数值计算比 GDScript 快，可直接用 64 位双精度浮点数（GDScript 的 `Vector4` 默认是 32 位），同时开发成本又比 C++ 省事。相应承担的代价是：用 C# 编写编辑器插件较为繁琐，且无法导出网页版。
