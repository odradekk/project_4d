# 序章白模实现

Status: accepted

## Problem

序章文档已经写完九个场景，但只有第 8、9 场在已归档的 three.js 原型里玩过。学校、日常段落和整段序章的节奏，从没在可玩的版本里验证过。正式项目用 Godot 和 C#，引擎和游戏项目目前只有空骨架。在投入建模、贴图和渲染之前，需要先把整段序章做成能玩的版本，确认设计站得住。

## Proposal

用白模在 Godot 里把序章九个场景完整做出来，验证场景布局、操作、谜题和节奏。表现层工作等序章试玩定稿后再做；白模阶段每样内容做到什么程度，见 Scope 一节。

场景不排先后顺序：完成标准是整段序章一次玩通，先做哪一场不影响结果。制作分三步展开：

1. 先串行完成三样基础，后面的线都依赖它们：
   - 框架文档「引擎模块」里七个接口分组（世界、实体、动作、推进、截面、查询、存档）的类型和方法签名；
   - 关卡标注格式，见 Decision note: 2026-10-26-region-scene-authoring；
   - 一个最小可玩版本：角色能在一个截面里走动，举起棱镜能看到另一个截面。
2. 基础完成后，四条线并行：
   - 引擎：四维几何、翻转规划与碰撞预检、接缝与手性、四维装置、四维物品、啃食者切片、通用查询；
   - 适配层与截面渲染：切片网格、碰撞形状、镜片画面，以及镜片里的轮廓、细光、预览线等标记；
   - 共用游戏系统：角色、猫、NPC、字幕、笔记本、占位音、调试启动；
   - 场景，按区域分为家和上学路、学校、小卖部、房间与深处。场景线可以先搭布局、写剧情流程；每个谜题等它用到的引擎功能做完，再接上。
3. 并行开始前加上 GitHub Actions CI，因为几条线要同时往主分支合并。每个 PR 都构建整个解决方案、运行引擎测试、检查文件大小；Godot 场景检查不放进 CI。

白模关卡由代理按序章文档和框架文档的尺寸规范，用盒子搭成 Godot 场景；设计者在编辑器里试玩，直接调整。框架文档要求人来审定谜题是否直观、公平，但没有要求人来摆盒子。

编辑器方面，白模阶段只做两样：引擎实现框架文档列出的数值规范校验，debug 构建载入关卡时报错；游戏内的调试视图，例如在镜片里切到任意截面。截面查看器、多截面对比、扫过范围可视化、被啃几何的离线预计算这些编辑器插件以后再做。

游戏层用什么语言，见 Decision note: 2026-10-26-game-layer-csharp。引擎数学怎么写、怎么测，见 Decision note: 2026-10-26-engine-rewrite。

序章文档里有两处要先改，一处和翻转面规则不一致，一处需要引擎的新能力：

- 第 4 场的橡皮改成原地翻面，字反过来，不再写“绕着桌沿翻过去”。第一次教翻面只讲一件事：翻过来，手性就反了；绕障碍翻面留到第 8 场再教。
- 第 5 场保留推拉窗，用沿轨道平移的四维装置实现，见 Decision note: 2026-10-26-device-translation。

## Scope

| 内容 | 白模阶段怎么做 | 原因 |
|---|---|---|
| 场景几何 | 只用盒子拼 | 楼房和物件在引擎里本来就由凸盒子零件组成，白模可以直接作为碰撞和切片数据 |
| 有手性意义的图案，如橡皮和逗猫棒上的字 | `Label3D` 或简单贴花 | 玩家要看得出左右反了 |
| 棱镜里的贯穿物发光轮廓、接缝细光、镜像缝翻转窄带、翻转预览线、隐藏结构虚线 | 纯色线条 | 这些是解谜要读的信息 |
| 老师、同桌、同学、猫 | 胶囊体加脚本移动，不做动画 | 老师巡视和猫的行为本身就是玩法 |
| 字幕、独白、翻转受阻时的提示语、数学笔记本 | 纯文字 | 要验证叙事节奏、受阻反馈和提示 |
| 粉笔声停、脚步声、啃食者的刮擦声和距离分层、隔着截面传来的闷响 | 占位音 | 躲老师和啃食者预警都靠声音 |
| 跨截面声音变闷 | 简单的低通滤波 | 玩家要能分辨声音来自哪个截面 |
| 啃食者 | 四维元球实时切片 | 结尾的节奏离不开它 |
| 被啃掉的几何 | 被咬的楼房元素整块隐藏 | 精确烘焙需要编辑器工具，序章里只有截面Ⅲ被咬 |
| 调试 | 从任意场景开始，预置笔记本页和背包 | 要反复试玩单个场景 |
| 失败重来 | 场景内检查点 | 被老师抓到只重来一小段 |

留到定稿以后做：PS1 渲染、贴图、正式建模、氛围光照、人物动画、其余环境声、被啃几何的精确烘焙、穿缝的挤压感和侧视闪现、存档。

## Alternatives considered

**按固定顺序做场景**，例如先做学校、先做原型里已有的第 8 和第 9 场，或者按剧情从第 1 场做到第 9 场。完成标准是整段一次玩通，先做哪一场不影响结果；固定顺序只会让本来可以同时做的工作排队。

**分场完成，美术按场提前开始。** 节奏和结尾反转只有整段连起来玩才能判断，所以美术要等序章定稿。

**每条线负责一个场景，从引擎一路做到剧情。** 几条线会同时改同一批引擎文件，冲突多，同一个功能还可能各做一套。

**按层分工，引擎、适配层、游戏层各一条线。** 每个功能都要穿过三层，几条线会互相等待。

**设计者在编辑器里亲手搭全部布局。** 九个场景的布局会让设计者成为并行的瓶颈。

**现在就做 Godot 编辑器插件。** 用 C# 写编辑器插件繁琐，会拖慢场景验证；白模阶段在游戏里用棱镜就能看清各个截面。

**第 4 场让橡皮绕障碍翻面**，比如以同桌立起来的课本为翻转面，让橡皮翻到小满这边。第一次教翻面只该讲一件事，而第 8 场还会教绕障碍翻面。

**不加 CI。** 几条线同时往主分支合并，只靠各自在本地检查，合并后才可能发现别的线把构建弄坏了。

## Acceptance criteria

- 序章第 1 到第 9 场能一次玩通，约 30 分钟，每个谜题都能解开。
- 所有谜题和剧情的触发条件都通过引擎的通用查询读取状态，没有针对单个谜题的特例判断。
- 引擎的四维数学有测试覆盖，期望值的来源见 Decision note: 2026-10-26-engine-rewrite。
- 每个 PR 都经过 CI 的构建、引擎测试和文件大小检查。
- 设计者试玩后，序章文档改为定稿；表现层工作从这之后开始。

## Risks

- 白模验证不了氛围。结尾反转的情绪很大程度上靠光线、PS1 画面和声音，白模阶段只能粗略判断，要等表现层做完才能真正判断；到那时如果情绪不成立，序章设计可能还要回头改。
- 代理搭出来的空间关系可能不顺手，设计者要在编辑器里多次调整。
- 被咬的楼房元素在白模里整块消失，和最终按四维减法切出平滑断面的效果不同，试玩时看到的啃食范围不代表最终效果。
